# 2. 의존성 주입을 하나씩 비교하기

목표: BookService가 사용하는 BookRepository를 누가 만들고 전달하는지 설명할 수 있습니다.

읽을 코드: `springbeanexampleV4/Application` → `book/BookService` → `BookRepository` → `MemoryBookRepository` → `Book`. 그다음 `BookServiceSetter`, 마지막으로 `BookServiceField`를 읽으세요.

이 예제는 main에서 서비스 메서드를 호출하고 도서를 출력합니다. `@Repository`로 저장소 빈을 등록하고, `@Service`로 서비스 빈을 등록하면 Spring이 필요한 저장소를 서비스에 전달합니다. 객체를 사용하는 쪽이 내부에서 직접 만들지 않고 외부에서 받는 것이 의존성 주입(DI)입니다.

## 2-1. 생성자 주입

BookService의 `@AllArgsConstructor`가 만드는 생성자는 아래 모양입니다. 기존 Lombok 문법을 실제 Java 생성자와 연결해 읽으세요.

```java
public BookService(BookRepository bookRepository) {
    this.bookRepository = bookRepository;
}
```

생성자가 하나이면 `@Autowired`를 생략할 수 있습니다. `final`은 필드 참조를 나중에 교체하지 못하게 합니다. 참조하는 객체 내부까지 모두 불변으로 만들지는 않습니다.

```bash
./gradlew bootRun -Plesson=di
```

도서 세 권과 1·2번 도서가 출력됩니다. 실제 DB 없이 메모리 목록을 읽습니다. `findAll()`은 목록을 복사해 반환하므로 호출자가 반환 목록을 비워도 저장소 목록 자체는 비워지지 않습니다.

## 2-2. setter 주입

main의 주석 안내에 따라 `BookServiceSetter` 조회 두 줄을 풀어 출력해 보세요. 생성 후 `@Autowired` setter를 호출하여 저장소를 넣습니다. `new BookServiceSetter()`만 하면 저장소는 아직 null입니다.

Spring의 `@Autowired`는 기본적으로 필수 주입입니다. setter 방식이라는 이유만으로 의존성이 없어도 실행되는 것은 아닙니다. `@Repository`를 제거하면 이 서비스도 필요한 빈을 찾지 못해 앱 시작이 실패할 수 있습니다.

## 2-3. 필드 주입

마지막으로 `BookServiceField`의 두 줄을 풀어 비교합니다. Spring이 필드에 저장소를 넣기 때문에 main에서 조회한 빈은 동작합니다. 반면 직접 `new`로 만든 객체에는 자동 주입되지 않습니다. 세 방식 중 생성자 주입은 필요한 의존성이 생성자에 드러나 읽기 쉽습니다.

## 작은 실패 실습

main의 `findBook(999)` 줄만 주석 해제해 실행하세요. `해당 도서가 없습니다.` 예외가 납니다. 이는 빈이 없는 것이 아니라 저장소에 해당 도서 데이터가 없는 상황입니다. 실습 후 주석으로 되돌리세요.

## 확인 질문

1. Spring 없이 `new MemoryBookRepository()`를 만들어 BookService 생성자에 전달할 수 있나요?
2. `@Autowired` 필드를 가진 객체를 직접 new 하면 주입되나요?

<details><summary>답</summary>

1. 가능합니다. DI는 일반 Java 생성자 호출로도 구현할 수 있습니다.
2. 자동 주입되지 않습니다. 컨테이너가 관리하는 객체를 기준으로 주입이 이루어집니다.

</details>
